## 1. 项目概述

### 1.1 背景

我国老龄化程度持续加深，独居老人数量快速增长。独居老人居家健康管理存在四个典型痛点：

1. **不会用**：智能设备与 App 的交互门槛高，老人不习惯打字、看不懂复杂界面。
2. **没人问**：子女不在身边，身体出现异常时无人察觉，求助链路长。
3. **看不出来**：心率、血压、血氧等指标单次看不异常，但"持续缓慢恶化"这种趋势没人帮他盯。
4. **通知不到**：真正发生风险时，家属往往最后一个知道，事后才发现。

现有"养老院机构版"系统面向护士站与统一管理，解决的是"机构内多位老人的流程标准化"问题，**不解决独居老人个人场景下的语音入口、趋势分析与家属闭环**。

### 1.2 项目目标

构建一套面向**独居老人居家场景**的健康管家多智能体系统，实现：

- **一句话问健康**：老人用语音说话即可完成健康问询，系统语音回播结果。
- **一个人盯趋势**：后端常驻检测服务，持续消费时序数据，用规则+趋势+离群三层检测发现风险。
- **一条链闭环**：从"语音输入 → 意图路由 → 数据检查 → 知识检索 → 风险分级 → 家属通知/语音播报"全自动闭环。
- **一份报告**：按 Skill 机制生成日报/周报，可下载 Word，家属可查。
- **一个安全边界**：JWT + RBAC + DAO 层数据隔离 + MCP 工具授权，杜绝越权访问健康数据。

### 1.3 与同类系统的差异（竞品/现状对比）

| 维度 | 养老院机构版（学长的系统） | 本系统（居家个人版） |
| :--- | :--- | :--- |
| 使用入口 | 护士在 PC 端录入、查询 | 老人语音说话（WebSocket + Vosk） |
| 通知对象 | 护士站轮班人员 | 直接通知绑定的家属 |
| 数据粒度 | 批量管理多位老人 | 聚焦个体时序数据趋势 |
| 部署形态 | 机构内网统一部署 | 家庭轻量部署（Docker Compose） |
| 核心能力 | 流程标准化、排班协同 | 语音交互 + 时序趋势分析 + 情感陪伴 |

## 2. 术语与缩略语

| 术语 | 说明 |
| :--- | :--- |
| Agent（智能体） | 具备独立职责、由 LLM 驱动的处理单元；本系统中一个节点即一个 Agent |
| Supervisor | 主管节点，集中调度所有 Worker，采用 `Command(goto=...)` 动态路由 |
| Worker | 执行具体任务的智能体节点（数据质检、风险判断、报告生成等） |
| Checkpointer | LangGraph 状态持久化组件，按 `thread_id` 隔离会话，本项目默认 `PostgresSaver`，开发态可切 `InMemorySaver` |
| Skill | 可被 LLM 按需加载的"技能包"，由 `SKILL.md`（元数据 + 指令）组成，采用渐进式披露 |
| MCP | Model Context Protocol，标准化工具调用协议；本项目工具独立部署在 MCP Server（端口 9000） |
| 四层记忆 | L1 窗口记忆（Redis）、L2 摘要记忆（PostgreSQL）、L3 长期记忆（Milvus）、L4 用户画像（Redis Hash） |
| 三层检测 | ①规则阈值检测 ②统计趋势检测 ③个性化离群检测 |
| 纯计算层 | `detect_anomaly()`，只判断不落库不发通知，保证手动/自动检测互不污染 |
| 双通道告警 | 通道 1：MCP 短信/邮件通知家属；通道 2：WebSocket 推送 + 语音播报告知老人 |
| 降级 | 主路径失败后自动切换备选路径（模型/工具/节点/RAG/服务/告警六个层面） |
| SSE | Server-Sent Events，服务端单向流式推送，用于 AI 回复打字机效果 |
| RBAC | 基于角色的访问控制（老人 / 家属 / 管理员） |

### 3.3 关键业务流程

**流程 A：语音健康问询（主链路）**

```
老人点击"语音" → WebSocket 建连 → Vosk 流式识别 → 前端拿到文本并自动发送
   → /chat (SSE) → LangGraph: Planner 拆任务 → Manager 调度
   → data_check(取最新体征+质检) → rag(知识检索) → risk(三层检测分级)
   → 汇总生成温和建议 → SSE 流式打字机 → EdgeTTS 生成语音 → 前端自动播报
```

**流程 B：后台自动预警（常驻链路）**

```
APScheduler/Celery Beat 每 5 分钟触发 → 遍历所有老人 → detect_anomaly(mode="auto")
   → 命中异常 → 写 alert_record(MySQL) → asyncio.gather 双通道并发
        ├─ 通道1：Celery 异步任务 → MCP 短信/邮件 → 家属（失败重试 3 次 × 60s）
        └─ 通道2：WebSocket 推送老人端 → 弹窗 + EdgeTTS 语音播报 + "我已知道"回执
```

**流程 C：手动健康问询（与自动检测隔离）**

```
老人问"我身体怎么样" → risk 节点调用 detect_anomaly(mode="manual")
   → 只返回结论与建议，不写 alert_record、不触发通知 → 由 Agent 组织语言回复
```

**流程 D：复合意图一次办完**

```
"帮我看看身体怎么样，然后生成周报，再告诉我中午吃啥"
   → Planner 拆解 [{vitals},{knowledge},{risk},{report,args:{type:weekly}},{chat}]
   → Manager 逐个取任务 → Worker 执行后把结果写入 task_results → 回 Manager
   → 队列空 → Summarize 节点整合成一段连贯回复
```

## 4. 项目范围

### 4.1 范围内（In Scope）

1. 语音输入（Vosk 离线识别）与语音输出（EdgeTTS）链路。
2. 多智能体编排（LangGraph Supervisor + Command 动态路由 + 任务队列）。
3. 健康数据接入与模拟（InfluxDB 时序数据 + 启动补历史 + 运行期每 10 分钟写入）。
4. 三层风险检测与分级预警（规则 / 趋势 / 离群）。
5. 健康知识库 RAG（解析→切分→向量化→Milvus→元数据过滤→Rerank→溯源）。
6. 用药计划与提醒（含漏服登记、邮件提醒 Skill）。
7. 家属通知闭环（MCP 短信/邮件 + WebSocket 实时告知 + 告警确认）。
8. 日报/周报生成（Skill 机制）与 Word 下载。
9. 四层记忆（窗口/摘要/长期/画像）与情感标签。
10. JWT + RBAC + DAO 数据隔离 + MCP 工具鉴权。
11. 六层降级策略与 `/health` 服务降级感知。
12. Docker Compose 一键部署（含 MySQL/PostgreSQL/Redis/InfluxDB/Milvus）。

### 4.2 范围外（Out of Scope）

1. 医疗器械级诊断结论（系统只做健康提示，不做诊断，不替代医生）。
2. 真实第三方设备（华为运动健康/小米手环）生产级对接——厂商接口未授权开放，改用 `huawei-health-mcp` 社区项目 + 公开数据集模拟。
3. 视频通话、跌倒视觉识别（V1.1 之后再评估）。
4. 短信网关的商务通道申请（开发期用邮件 + 控制台模拟通道）。
5. 多租户 SaaS 计费与运营后台。

## 5. 功能需求

> 需求优先级：**P0** = MVP 必须交付；**P1** = 完整版交付；**P2** = 增强项。
> 每条需求均给出可验证的验收依据，便于测试用例映射。

### 5.1 FR-01 语音输入（WebSocket 实时识别）· P0

| 项 | 内容 |
| :--- | :--- |
| 描述 | 提供 `ws://host/voice/ws` 长连接，前端推送音频/触发识别，服务端基于 Vosk `KaldiRecognizer`（16kHz、4096 帧）流式识别，检测到一句结束即主动推送识别文本 |
| 输入 | WebSocket 连接 + 启动/停止指令 |
| 输出 | `{"type":"asr","text":"我今天血压怎么样","final":true}` |
| 约束 | 4096/16000 ≈ 0.256s，延迟与性能平衡点；必须支持**连续多句识别**与**随时停止** |
| 验收 | AC-01、AC-02 |

**关键设计（吸取的历史缺陷）**：识别到第一句后不得退出循环。职责拆分——`send_msg()` 只负责发送，`stop()` 只负责停止监听；用 `asyncio.create_task()` 把识别放后台任务，主协程继续 `receive_text()` 响应"停止"指令，实现"持续识别 + 随时可控"。

### 5.2 FR-02 文本/语音双入口统一问询 · P0

| :--- | :--- |

| 输出 | SSE 事件 `{"data":"片段","done":false}`，最后 `{"data":"","done":true}` |

### 5.5 FR-05 情感识别与陪伴 · P1

| 验收 | AC-07 |

### 5.6 FR-06 生命体征时序检测（三层）· P0

| 层 | 名称 | 逻辑 | 输出 |
| :--- | :--- | :--- | :--- |
| 第一层 | 规则阈值检测 | 硬阈值判定：心率 >120 或 <50；收缩压 >180 或 <90；舒张压 >110；血氧 <90%；体温 >37.3℃ 或 <36.0℃；空腹血糖 >7.0 或 <3.9 | 高危/中危异常项 |
| 第二层 | 统计趋势检测 | 取近 7 天数据计算移动平均与变化率；当前值偏离 7 日均值超过 30% 记为"异常趋势"；连续 3 天同向偏离 → 升级"中危预警" | 趋势异常项 |
| 第三层 | 个性化离群检测 | 基于 MAD（中位数绝对偏差）/孤立森林学习个体基线，超出个体正常分布范围记为离群 | 离群异常项 |

| 项 | 内容 |
| :--- | :--- |
| 描述 | `detect_anomaly(user_id, mode)` 为**纯计算层**：只读取 InfluxDB 与计算，**不写库、不发通知、不改状态**；`mode` 只影响日志，不影响检测逻辑 |
| 分级 | 规则命中 → 高危；趋势异常/离群 → 中危；连续 3 天偏离 → 中危；否则正常 |
| 验收 | AC-08、AC-09、AC-10 |

### 5.7 FR-07 分级预警与家属通知闭环 · P0

| 项 | 内容 |
| :--- | :--- |
| 描述 | ①自动检测命中后写 `alert_record`；②`asyncio.gather` 并发触发双通道；③高危立即通知，中危汇总后批量通知（降低误报噪音）；④家属可在前端确认告警形成闭环 |
| 通道 1 | Celery 异步任务 → MCP `send_sms` / `send_email` 工具 → 家属；失败按 `max_retries=3, countdown=60s` 重试，全失败写日志并落本地待发队列 |
| 通道 2 | WebSocket 推送老人端（含 RAG 检索到的处置建议），前端弹窗 + 自动语音播报 + "我已知道"回执 |
| 人工介入 | 当 `AUTO_NOTIFY_SMS=false` 时，高危 SMS 不直接发出，置 `need_human_confirm=True`，由家属在 `/alert/{id}/confirm` 确认后再发 |
| 验收 | AC-11、AC-12 |

### 5.8 FR-08 健康报告生成与下载 · P1

| 项 | 内容 |
| :--- | :--- |
| 描述 | 按 `daily_report` / `weekly_report` Skill 生成报告：指标概览（均值/最值/趋势）、异常与告警汇总、用药依从性、RAG 依据的个性化建议；支持导出 Word |
| 接口 | `GET /report/daily?user_id=`、`GET /report/weekly?user_id=`、`GET /report/download?user_id=&type=` |
| 验收 | AC-13 |

### 5.9 FR-09 健康知识库 RAG 与溯源 · P0

| 阶段 | 说明 |
| :--- | :--- |
| 数据准备 | 用药指南、慢病管理文档（PDF/Word/Markdown）→ 解析 → 按语义切分（512 字符 + 100 重叠）→ Embedding |
| 入库 | 向量 + 元数据（来源/版本/病种/页码）写入 Milvus，建 HNSW 索引 |
| 检索 | 问题向量化 → Milvus 召回 Top-K → 元数据过滤（病种/药物）→ Rerank 精排 → 返回 `content + source + version + page + score` |
| 溯源 | 所有健康建议均携带来源与段落定位，前端可展开"依据" |
| 降级 | 向量检索失败 → 关键词检索（MySQL `knowledge_doc`）→ 静态建议（"请咨询专业医生，紧急情况拨打 120"） |
| 验收 | AC-14、AC-15 |

### 5.10 FR-10 复合意图任务队列编排 · P1

| 项 | 内容 |
| :--- | :--- |
| 描述 | Planner 节点用 LLM 把请求拆成**有序任务列表**（只允许从白名单任务类型中选择），写入 `state.task_queue`；Manager 每次 `pop(0)` 取一个任务，用 `Command(update=..., goto=...)` 动态路由到 Worker；Worker 写 `task_results` 后回到 Manager；队列空后进入 Summarize 整合 |
| 任务白名单 | `vitals` / `knowledge` / `risk` / `medication` / `report` / `notify` / `emotion` / `chat` |
| 兜底三层 | ①Planner 提示词约束可选任务 → ②Manager 二次校验，未知任务降级 `chat` 并记日志 → ③chat 无法处理时反问用户澄清 |
| 退化兼容 | 单任务请求队列长度为 1，等价于固定单路径，无需额外分支 |
| 验收 | AC-16、AC-17、AC-18 |

### 5.11 FR-11 身份认证与数据权限 · P0

| 项 | 内容 |
| :--- | :--- |
| JWT | 登录签发 Token（含 `user_id`、`role`、`exp`），前端 `Authorization: Bearer <token>`；服务端校验签名与有效期 |
| RBAC | 老人：仅本人数据；家属：绑定的老人数据 + 接收通知；管理员：用户/设备/知识库管理 |
| 数据权限 | DAO 层强制拼接 `where user_id = 当前用户（或其绑定老人）`，从根上防横向越权 |
| 工具权限 | MCP Server 用 `KeyVerifier` 校验 `MCP_API_KEY`，未授权工具调用直接拒绝 |
| 输入校验 | Pydantic 校验所有入参类型与范围；SQL 全部参数化，禁止字符串拼接 |
| 验收 | AC-19、AC-20、AC-21 |

### 5.12 FR-12 Skill 技能机制（渐进式加载）· P1

| 项 | 内容 |
| :--- | :--- |
| 描述 | 技能以目录形式存放：`app/skills/registry/<skill_name>/SKILL.md`，含 YAML 元数据（`name`、`description`）与指令正文。Agent 启动时只加载元数据（轻量）；LLM 判断问题匹配某技能后调用 `load_skill(skill_name)` 拉取完整指令，再按指令依次调用 MCP 工具/本地工具 |
| 内置技能 | `medication_reminder`（用药提醒邮件）、`weekly_report`（周报）、`daily_report`（日报）、`emotion_comfort`（情感安慰） |
| 执行示例 | "帮我给张三发一封用药提醒邮件" → 匹配 `medication_reminder` → `load_skill` → `get_user_profile`（MCP）→ `get_medication_schedule`（MCP）→ `send_email`（本地工具）→ 汇总回复 |
| 验收 | AC-22 |

### 5.13 FR-13 四层记忆与多轮上下文 · P1

| 层 | 存储 | 内容 | 读写时机 |
| :--- | :--- | :--- | :--- |
| L1 窗口记忆 | Redis List | 最近 N 轮原文（默认 10 轮，TTL 1 天） | 每轮对话后 `rpush + ltrim` |
| L2 摘要记忆 | PostgreSQL | 会话历史摘要（`conversation_summary`，按 `session_id` upsert） | 窗口消息 ≥ 2 条时由 `SummaryAgent` 增量更新 |
| L3 长期记忆 | Milvus（`long_memory`，失败降级 ChromaDB） | 值得长期记住的事实（偏好、慢病史、家庭情况） | 每轮对话后由 `LongAgent` 提取写入，检索时按 `user_id` 过滤 |
| L4 用户画像 | Redis Hash | 结构化属性（姓名/年龄/慢病/过敏/紧急联系人/沟通偏好） | `ProfileAgent` 结构化抽取后 `hset` |
| 组装 | — | `PromptBuilder` 把四层拼成 system 提示词注入图输入 | 图执行前 |

| 项 | 内容 |
| :--- | :--- |
| 会话隔离 | Checkpointer `thread_id = session_id`，会话归属校验（Redis `session:<uuid>` 存 `user_id`），同一会话加 Redis 分布式锁防并发串话 |
| 验收 | AC-23、AC-24 |

### 5.14 FR-14 健康数据接入与连续性保障 · P0

| 项 | 内容 |
| :--- | :--- |
| 数据来源 | ①`huawei-health-mcp` 社区项目（替代厂商未授权接口）②公开数据集（老年康养行为数据、CAREUP-IC、MIMIC、PhysioNet、DiaBD、BUT PPG）③内置数据模拟器 |

| 保留期 | 数据库创建时设 `--retention-period 30d`（InfluxDB 3 Core 不支持按点删除，只能用保留期） |
| 验收 | AC-25 |

## 6. 非功能需求

### 6.1 性能（NFR-01）

| 指标 | 目标值 | 说明 |
| :--- | :--- | :--- |
| SSE 首字延迟（TTFT） | ≤ 3s | 从请求到首个文本片段 |
| 文本问询端到端（不含语音） | ≤ 15s（P95） | 含一次知识检索 + 一次风险判断 |
| 语音识别出字延迟 | ≤ 1s（一句结束后） | Vosk 本地识别 |
| TTS 生成返回 | ≤ 3s / 100 字 | EdgeTTS 在线合成 |
| 自动检测吞吐 | ≥ 1000 老人 / 5 分钟轮次 | 并发 + 简化查询 |
| 时序写入 | 单实例 ≥ 500 点/秒 | 批量写入 |

### 6.2 可用性与降级（NFR-02）

- 单个依赖（Milvus / InfluxDB / MCP Server）不可用时，系统**必须**降级而非报错崩栈。
- `/health` 必须真实探测 MySQL、PostgreSQL、Redis、InfluxDB、Milvus、MCP Server 六项。
- 高危告警必须"至少一次送达"：短信 → 邮件 → 备用网关 → Celery 重试 → 本地队列，五级兜底且全程留痕。

### 6.3 安全（NFR-03）

| 项 | 要求 |
| :--- | :--- |
| 认证 | JWT（HS256，默认 24h 过期），签名与过期双校验 |
| 授权 | RBAC 三角色 + DAO 层 `user_id` 强制过滤 |
| 工具边界 | MCP Server `KeyVerifier` 校验 Token，白名单工具表 |
| 传输 | 生产启用 HTTPS/WSS，CORS 白名单 |
| 密钥 | 全部置于 `.env`，`MCP_API_KEY` 不入前端；`.env` 不进 Git |
| SQL | 参数化查询；禁用 DELETE/UPDATE/INSERT/DROP/CREATE/ALTER 由 LLM 生成的语句 |
| 隐私 | 健康数据脱敏日志（手机号/邮箱中间打码），不留存原始音频 |

### 6.4 可观测性（NFR-04）

- 关键节点进出日志（节点名、`user_id`、`session_id`、耗时、`health_step`）。
- 未知任务日志：`task_name / args / user_id / timestamp`，用于反推 Planner 提示词是否需要调整。
- 降级事件必须 `WARNING`/`CRITICAL` 级别记录，便于追查。
- 告警记录可统计：按用户、按类型、按级别、按天聚合。

### 6.5 兼容性与部署（NFR-05）

- 后端 Python 3.11+；前端 Vue（CDN 版，无需 Node 构建）。
- 一键部署：`docker compose up -d` 拉起 MySQL 8 / PostgreSQL 16 / Redis 7 / InfluxDB 3 Core / Milvus 2.4 / MCP Server / 后端。
- Windows 开发态需设置 `asyncio.WindowsSelectorEventLoopPolicy()`（Vosk/PyAudio 兼容）。
- 浏览器支持 Chrome / Edge 最新版。

### 6.6 可维护性（NFR-06）

- 分层解耦：Agent 与工具（MCP）、业务与数据库（DAO）、主流程与通知（Celery）、配置与代码（`.env` + YAML 提示词）、会话状态与图执行（Checkpointer 插件式）。
- 提示词外置到 `app/ai/prompt/*.yaml`，改提示词不改代码。
- 目录结构、命名与《开发规范与接口契约》保持一致，新人可 1 天内跑通。

节点职责与提示词要素：

| 节点 | 职责 | 关键提示词要素 | 主要输出状态字段 |
| :--- | :--- | :--- | :--- |
| `planner` | 复合意图拆解 | "只能从白名单任务中选择，不允许编造；多个需求拆多个任务，按用户表述顺序" | `task_queue` |
| `manager` | 主管调度 | 无提示词（纯代码决策） | `task_queue`、`current_task`、路由 `goto` |
| `intent` | 意图识别 + 情感标签 | "判断意图与情绪，输出结构化结果" | `intent`、`emotion` |
| `data_check` | 取最新体征 + 数据质检 | "检查心率、血压完整性，缺失则标记需补充" | `vitals`、`data_available`、`data_missing` |
| `rag` | 知识检索 | "根据问题检索用药指南/慢病管理文档，返回来源与段落" | `knowledge` |
| `risk` | 三层检测与分级 | "心率>120 或血压>180 为高危；结合近 7 天趋势与个体离群判断" | `risk_level`、`risk_reasons`、`anomaly` |
| `report` | 日报/周报生成（Skill） | 按 `weekly_report`/`daily_report` Skill 指令组织章节 | `report_type`、`report_content` |
| `remind` | 用药提醒生成 | "查询用药计划，生成今日提醒内容，标注漏服" | `medication_list`、`remind_content` |
| `notify` | 双通道告警通知 | "生成简洁的通知文案，含异常描述与紧急建议" | `notify_channel`、`notify_result` |
| `summarize` | 多任务结果汇总 | "按用户提问顺序整合成一段连贯、友好的回复" | `final_answer` |
| `chat` | 兜底聊天 / 情感陪伴 | 情感标签为 anxious/low/lonely 时先安抚再建议；未知任务时反问澄清 | `final_answer` |

## 8. 数据需求

### 8.1 存储选型与职责

| 存储 | 存什么 | 为什么这么选 |
| :--- | :--- | :--- |
| **MySQL** | 用户、健康档案、家属绑定、用药计划/记录、告警记录、知识文档 | 结构化、需事务、需关联查询 |

| **InfluxDB 3** | `vital_signs` 时序点 | 时间优先存储、按范围聚合快、内置降采样、支持保留期 |

| `health_profile` | `user_id`、`age`、`gender`、`disease_history`、`allergy`、`emergency_contact`、`emergency_phone` |
| `medication` | `id`、`user_id`、`drug_name`、`dosage`、`frequency`、`take_time`、`start_date`、`end_date` |
| `medication_record` | `id`、`user_id`、`medication_id`、`plan_time`、`actual_time`、`status`(待服/已服/漏服) |
| `alert_record` | `id`、`user_id`、`alert_type`、`level`、`value`、`description`、`source`(auto/manual)、`status` |

### 8.3 时序数据模型

```
measurement: vital_signs
  tag:   user_id, source(device/simulator/huawei)
```

### 8.4 Redis Key 约定

| :--- | :--- | :--- | :--- |

| `pending_sms` | List | 模拟短信待发队列（未接真实短信网关） | 长期 |

## 10. 关键技术方案

### 10.1 为什么用 LangGraph 而不是直接用 LangChain Agent

本场景有**明确的多阶段流程**（语音→意图→查数据→检索→风险评估→通知），且需要**在关键节点（发通知前）暂停等人确认**。LangGraph 提供三个 LangChain Agent 不具备的能力：

1. **状态图可控**：节点职责明确，路由逻辑可写死，不依赖 LLM 临场判断。
2. **原生循环与中断**：可"数据缺失→补查"回到前序节点；可中断等人确认。
3. **Checkpointer 记忆**：按 `thread_id` 持久化，同一老人多轮有上下文，跨用户不串。

### 10.2 Supervisor + Command(goto) 与条件边的取舍

- **条件边**：路由逻辑写在节点外的独立函数，靠映射表跳转，编译期结构固定。
- **Command(goto=...)**：路由逻辑写在节点内部，运行时决定去向，并可同时 `update` 状态。

本项目选 `Command`：状态机式决策集中在主管节点、无需维护映射表、避免节点间直连耦合。代价是路由集中，需依赖主管节点做兜底校验（已在 FR-10 中列为三层防御）。

### 10.3 手动检测与自动检测为什么不会互相污染

把检测拆成 **纯计算层** 与 **副作用层**：

```
detect_anomaly(user_id, mode)  ← 纯计算：只读 InfluxDB + 计算，不写库、不发通知
        ├── mode="auto"   → 写 alert_record + 双通道通知 + 更新状态
        └── mode="manual" → 只把结论返回给 Agent，由 Agent 回复老人
```

两者**检测逻辑与数据来源完全一致**，差异只在**副作用**。老人主动问询不会写告警库、不会触发通知，因此不会污染自动检测的统计口径。

### 10.4 复合意图：从"单意图路由"升级为"多意图编排"

主管节点从"固定 if-else"改为"从 `task_queue` 取任务"，Worker 完成后回主管，队列空后 Summarize 汇总。单任务请求队列长度为 1，自然退化为原单路径流程，架构不变。

### 10.5 传播协议选型

| 场景 | 协议 | 原因 |
| :--- | :--- | :--- |
| 前端→后端普通请求 | HTTP | 标准 REST |
| 后端→前端 AI 流式回答 | **SSE** | 单向推送、实现简单、浏览器自动重连，适合打字机效果 |
| 前端↔后端语音流 | **WebSocket** | 全双工长连接、可传二进制音频、服务端主动推识别结果 |
| Agent→MCP Server | MCP over HTTP/SSE | 标准工具协议，工具可独立部署复用 |
| 主流程→通知任务 | Redis 队列（Celery） | 异步解耦，耗时 IO 不阻塞主流程 |
| Checkpointer→存储 | PostgreSQL 连接池 | 状态持久化，跨进程恢复 |

### 10.6 语音链路

- **输入**：WebSocket 长连接 → 前端触发 → Vosk `KaldiRecognizer(model, 16000)` 流式 `AcceptWaveform(4096 帧)`，返回 `True` 表示一句结束 → `json.loads(re.Result())["text"]` → `ws.send_text`。
- **输出**：EdgeTTS `Communicate(text, "zh-CN-XiaoxiaoNeural")` → mp3 落盘 → 返回 URL → 前端 `Audio` 自动播放。
- **职责单一**：`send_msg()` 只发消息，`stop()` 只停监听；识别放 `asyncio.create_task` 后台任务，主协程继续收指令。

### 10.7 知识库构建流程

```
文档（PDF/Word/MD） → 解析（抽取文本+页码） → 语义切分（512 字符 + 100 重叠）
→ Embedding → 写入 Milvus（向量 + 元数据：source/version/disease_type/page）
→ 建 HNSW 索引 → 检索：向量化 → Top-K 召回 → 元数据过滤 → Rerank 精排 → 返回溯源结果
```
