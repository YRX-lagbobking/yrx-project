## 2. LangGraph 状态机（编排层细节）

```
                            START
                              │
                              ▼
                    ┌───────────────────┐
                    │     planner       │  LLM 把请求拆成有序任务列表
                    │  （任务拆解）      │  写入 task_queue（只允许白名单任务）
                    └─────────┬─────────┘
                              │
                              ▼
              ┌───────────────────────────────┐
        ┌────►│           manager             │  纯代码决策（无提示词）
        │     │  ① 失败任务重试（<3 次）       │
        │     │  ② queue 为空 → 去向判断       │
        │     │  ③ queue.pop(0) → goto 对应 Worker
        │     └───────┬───────────────────────┘
        │             │
        │   ┌─────────┼─────────┬─────────┬─────────┬─────────┬─────────┐
        │   ▼         ▼         ▼         ▼         ▼         ▼         ▼
        │ ┌──────┐┌────────┐┌──────┐┌──────┐┌──────┐┌──────┐┌──────┐┌──────┐
        │ │intent││data_   ││ rag  ││ risk ││report││remind││notify││ chat │
        │ │意图+ ││check   ││知识  ││三层  ││日报  ││用药  ││双通道││兜底/ │
        │ │情感  ││体征+   ││检索  ││检测  ││周报  ││提醒  ││告警  ││陪伴  │
        │ │      ││质检    ││      ││分级  ││      ││      ││      ││      │
        │ └──┬───┘└───┬────┘└──┬───┘└──┬───┘└──┬───┘└──┬───┘└──┬───┘└──┬───┘
        │    │        │        │       │       │       │       │       │
        └────┴────────┴────────┴───────┴───────┴───────┴───────┴───────┘
                                    （Worker 完成后一律回到 manager）

        manager 的三种去向：
          · 有任务              → goto 对应 Worker
          · 队列空 且 无结果     → goto summarize
          · 队列空 且 仅 chat    → goto END
          · 队列空 且 多任务     → goto summarize ──► END
          · 任务失败且重试 ≥3 次 → goto chat（降级兜底）
          · 未知任务（AC-17）    → 记为 {"task":"chat"} + logger.warning → goto chat
```

**为什么用 `Command(goto=...)` 而不是条件边？**

| 维度 | 条件边 | Command(goto)（本项目采用） |
| :--- | :--- | :--- |
| 路由位置 | 节点外的独立函数 + 映射表 | 节点内部，运行时决定 |
| 状态更新 | 需要额外节点返回 | 可与路由在同一次返回里 `update` |
| 扩展性 | 每加一个节点都要改映射表 | 只改主管节点一处 |
| 代价 | 结构固定、直观 | 路由集中，必须靠主管做兜底校验（已在 FR-10 做三层防御） |

## 4. 数据连续性策略（FR-14）

```
   问题：数据是"持续产生"的（设备/模拟器），但服务是"不常驻"的（开发机、容器重启）
         → 断档后趋势分析窗口不足，第二层检测失效

   对策：两段式补齐

   ┌────────────────────────────── 服务启动时（一次性） ──────────────────────────────┐
   │  lifespan → _start_vitals_data()                                              │
   │     for user_id in UserDAO.list_elders():                                      │
   │         write_history(user_id, days=VITALS_BACKFILL_DAYS(7),                   │
   │                       interval_minutes=VITALS_INTERVAL_MINUTES(10))            │
   │     → 按 10 分钟粒度回填近 7 天（7×24×6 = 1008 点/人）                          │
   │     → InfluxDB 不可用时只 warning，不阻断启动                                   │
   └───────────────────────────────────────────────────────────────────────────────┘
                                          │
                                          ▼
   ┌────────────────────────────── 运行期（常驻后台任务） ────────────────────────────┐
   │  start_simulator(elders)：asyncio 后台任务，每 10 分钟为每位老人写一条           │
   │  → 保证任何时刻 query_range(days=7) 都能拿到连续窗口                            │
   └───────────────────────────────────────────────────────────────────────────────┘

   时序模型：
     measurement : vital_signs
     tag         : user_id, source(device / simulator / huawei)
     field       : heart_rate, blood_pressure_sys, blood_pressure_dia, spo2,
                   temperature, glucose, sleep_hours
     time        : 10 分钟粒度
     保留期       : 建库时 --retention-period 30d
                   （InfluxDB 3 Core 不支持按点删除，清理脏数据只能靠保留期，风险 R-02）
```

## 5. 六层降级策略总览（FR-15 / NFR-02）

| 层面 | 主路径 | 降级 1 | 降级 2 | 降级 3 | 实现位置 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **模型** | 云端主模型（qwen3-max） | 云端备用模型（deepseek-chat） | 本地 Ollama（qwen2.5:3b） | 静态兜底文案 | `app/core/fallback.py`、`MyModel.get_text_by_fallback` |
| **工具** | MCP 远程工具（9000） | 本地纯函数实现 | 缓存结果（Redis） | 本地待处理队列 | `app/core/fallback.py`、`app/ai/tool/mcp_tool.py` |
| **节点** | 完整逻辑 | 简化逻辑（如 `detect_latest`） | 返回"未知" | — | `app/ai/agent/multi_agent/node/*` |
| **RAG** | 向量 + Rerank（Milvus） | 关键词检索（MySQL `knowledge_doc`） | 静态建议（"咨询医生，紧急 120"） | — | `app/ai/tool/rag_tool.py` |
| **服务** | 全功能（`mode=full`） | 部分功能（`partial`） | 只读模式（`readonly`） | 静态页面 | `app/core/health_check.py`、`GET /health` |
| **告警** | MCP 短信 | MCP 邮件 | 备用网关 | Celery 重试 / 本地队列 | `app/core/task/notify_task.py` |

### 5.1 服务降级与前端联动

```
   GET /health（无需鉴权）
        │
        ▼
   check_all() 真实探测 6 项依赖
        mysql / postgres / redis / influxdb / milvus / mcp_server
        │
        ▼
   detect_mode(status) → "full" | "partial" | "readonly"
        │
        ▼
   {"status": "healthy|degraded|critical", "mode": "...", "detail": {…}}
        │
        ▼
   前端（四个页面 mounted 时都会拉一次 /health）：
        full     → 顶部绿色"服务正常"
        partial  → 顶部黄色"部分功能降级"横幅

```

**故障注入演示（AC-26）**：`docker compose stop milvus mcp-server` →
`/health` 返回 `degraded / partial`，聊天功能仍可用（模型、MySQL、Redis 都在）。

## 6. 检测分层与"手动/自动互不污染"（FR-06）

```
                    detect_anomaly(user_id, mode)   ← 纯计算层（无副作用，AC-10）
                                  │
        ┌─────────────────────────┼─────────────────────────┐
        ▼                         ▼                         ▼
  ①规则阈值检测              ②统计趋势检测              ③个性化离群检测
  rule_detector              trend_detector             outlier_detector
  · 心率 >120 / <50          · 近 7 天移动平均          · MAD（中位数绝对偏差）
  · 收缩压 >180 / <90        · 变化率 > TREND_DEVIATION  · 孤立森林学习个体基线
  · 舒张压 >110              · 连续 3 天同向偏离         · 超出个体正常分布 → 离群
  · 血氧 <90                   → 描述升级"连续 N 天"       命中 → level="中危"
  · 体温 >37.3 / <36.0          （level 仍为中危）
  · 血糖 >7.0 / <3.9
        命中 → level="高危"
        │                         │                         │
        └─────────────────────────┴─────────────────────────┘
                                  ▼
                   list[dict]（固定结构）：
                   {"type": "heart_rate_high", "level": "高危", "value": 140,
                    "metric": "heart_rate", "description": "…", "source": "rule"}

   分级：规则命中 → 高危（硬阈值意味着已超出安全范围）；趋势异常 / 离群 / 连续 3 天偏离 → 中危；否则正常
        （说明：`settings.thresholds` 里的 `sleep_low` 只用于展示，契约第 7 节的 type 白名单
          没有睡眠项，因此规则层不产生睡眠异常，避免出现契约外的 type）

   ┌──────────────────────────── 关键设计：副作用分离 ────────────────────────────┐
   │  mode="auto"   → detect_task.auto_detect_all 调用 → 写 alert_record + 双通道通知 │
   │  mode="manual" → risk 节点 / POST /alert/detect 调用 → 只返回结论              │
   │                                                                            │
   │  两者检测逻辑与数据来源**完全一致**，差异只在副作用。                          │
   │  因此老人主动问询不会写告警库、不会触发通知，不污染自动检测的统计口径（AC-10）。 │
   └────────────────────────────────────────────────────────────────────────────┘
```

## 7. 四层记忆与提示词组装（FR-13）

```
   ┌────────────────────────────────────────────────────────────────────────┐
   │ L1 窗口记忆   Redis List  window_memory:{session_id}                   │

   ├────────────────────────────────────────────────────────────────────────┤
   │ L4 用户画像   Redis Hash profile:{user_id}                             │

                                   ▼
                    PromptBuilder.builder_prompt(user_id, question)
                                   │
                                   ▼
                {"role": "system", "content": "<四层拼合的提示词>"}
                                   │
                                   ▼
                        注入 LangGraph 图输入（memory_prompt）

   会话隔离：Checkpointer thread_id = session_id
             Redis session:{uuid} 记录会话归属（校验 session 属于当前 user_id）
```

## 8. 语音链路（FR-01 / FR-03）

```
   输入（浏览器 → 服务端）
   ─────────────────────────────────────────────────────────────
   点"开启语音" → new WebSocket("ws://host/voice/ws")
        │
        ▼
   服务端：VoskAgent.get_vosk()
        · asyncio.create_task(speak(ws))   ← 识别放后台任务，不阻塞主协程
        · 主协程继续 await ws.receive_text() 响应"停止"指令
        │
        ▼
   PyAudio 16kHz / 单声道 / 4096 帧（≈0.256s）
        │
        ▼
   KaldiRecognizer(model, 16000).AcceptWaveform(4096)
        · 返回 True → 一句结束 → json.loads(re.Result())["text"] → ws.send_text
        · ⚠️ send_msg() 只负责发送，**不得**设置 listening=False
        · 停止只能走 stop()；识别循环支持连续多句（AC-01）
        │
        ▼
   前端收到文本 → 填输入框 → 自动 send() → SSE /chat

   输出（服务端 → 浏览器）
   ─────────────────────────────────────────────────────────────
   回答结束 / 收到告警 → POST /voice/tts {"text": "..."}
        │
        ▼
   TTSAgent.speak(text) → edge_tts 合成 zh-CN-XiaoxiaoNeural → mp3
        │  落盘 app/html/tts/xxx.mp3（/static/tts/xxx.mp3 可访问）
        ▼
   返回 {"audio": "/static/tts/xxx.mp3"}
        │
        ▼
   前端 new Audio(url).play() 自动播报
   （音频/模型不可用时记录日志 + 发一条提示文本，正常返回，不抛异常）
```

## 9. 知识库 RAG 流程（FR-09）

```
   文档（PDF / Word / Markdown，含用药指南、慢病管理资料）
        │
        ▼  解析（抽取文本 + 页码 + 标题）
        │
        ▼  语义切分（CHUNK_SIZE=512 字符 + CHUNK_OVERLAP=100）
        │
        ▼  Embedding（text-embedding-v3，DashScope 兼容接口）
        │
        ▼  写入 Milvus health_knowledge
        │    向量 + 元数据：source / version / disease_type / page
        │
        ▼  建 HNSW 索引
   ──────────────────────────────────────────────────────
   检索：
   问题 → 向量化 → Milvus Top-K 召回 → 元数据过滤（病种/药物）
        → Rerank 精排（gte-rerank）
        → 返回 [{"content","source","version","page","score"}]   ← 每条可溯源（AC-14）

   降级链（AC-15）：
   向量+重排 ──失败──► 关键词检索（MySQL knowledge_doc）
                    ──失败──► 静态建议"请咨询专业医生，紧急情况拨打 120"
                               （全程日志 WARNING，接口保持可用）
```

## 10. 存储选型对照表（需求文档 8.1）

| 存储 | 存什么 | 为什么这么选 |
| :--- | :--- | :--- |
| **MySQL** | 用户、健康档案、家属绑定、用药计划/记录、告警记录、知识文档 | 结构化、需事务、需关联查询；`user_id` 强制过滤做数据权限 |
| **PostgreSQL** | 摘要记忆 `conversation_summary`、LangGraph Checkpointer 表 | LangGraph 官方支持；事务与并发可靠 |
| **Redis** | 窗口记忆（List）、用户画像（Hash）、会话（String）、分布式锁、缓存、Celery 队列 | 高频读写 + TTL + 原子操作 |
| **Milvus** | 健康知识向量（`health_knowledge`）、长期记忆（`long_memory`） | 语义检索 + 元数据过滤混合查询，可水平扩展 |
| **InfluxDB 3** | `vital_signs` 时序点 | 时间优先存储、按范围聚合快、支持保留期 |
| **ChromaDB** | 长期记忆降级向量库 | 无 Milvus 时的零依赖替代（本地文件） |
