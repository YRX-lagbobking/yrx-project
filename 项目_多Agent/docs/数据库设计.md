# 数据库设计

> 本文是《需求文档》8.1 / 8.2 / 8.3 / 8.4 与《开发规范与接口契约》第 8 节的展开版，
> 与 `sql/init.sql` **逐字段对应**。字段名改动必须先改 `sql/init.sql` 与本文，再同步 DAO。

---

## 0. 存储总览

| 存储 | 数据库 / 集合 | 存什么 | 选型理由 |
| :--- | :--- | :--- | :--- |
| MySQL 8 | `health_butler` | 8 张业务表 | 结构化、需事务、需关联查询 |
| PostgreSQL 16 | `postgres` | `conversation_summary`、LangGraph Checkpointer 表 | LangGraph 官方支持，事务与并发可靠 |
| Redis 7 | db 0 | 窗口记忆 / 画像 / 会话 / 锁 / 兜底队列 | 高频读写 + TTL + 原子操作 |
| Milvus 2.4 | `health_knowledge`、`long_memory` | 知识向量、长期记忆向量 | 语义检索 + 元数据过滤 |
| InfluxDB 3 Core | `agent_db` | `vital_signs` measurement | 时间优先存储、按范围聚合快、支持保留期 |
| ChromaDB | `./app/chroma_db` | 长期记忆降级向量库 | 无 Milvus 时的零依赖替代 |

## 1. MySQL 表结构

> 全部 `utf8mb4 / utf8mb4_general_ci`；`user` 是保留字，**表名与字段一律加反引号**。

### 1.1 `user` —— 用户表

角色：`elder` 老人 / `family` 家属 / `admin` 管理员。

| 字段 | 类型 | 说明 | 约束 |
| :--- | :--- | :--- | :--- |
| `user_id` | VARCHAR(32) | 用户编号（u001/f001/admin） | **PK** |
| `user_name` | VARCHAR(64) | 登录用户名 | NOT NULL，**UNIQUE** `uk_user_name` |
| `password` | VARCHAR(128) | 密码哈希 `sha256("health_butler" + 明文)` | NOT NULL，默认 `''` |
| `email` | VARCHAR(128) | 邮箱（家属通知、用药提醒邮件用） | NOT NULL，默认 `''`，索引 `idx_user_email` |
| `phone` | VARCHAR(20) | 手机号（日志脱敏） | NOT NULL，默认 `''` |
| `role` | VARCHAR(16) | `elder` / `family` / `admin` | NOT NULL，默认 `elder`，索引 `idx_user_role` |
| `status` | TINYINT | 1 正常 / 0 停用 | NOT NULL，默认 1 |
| `create_time` | DATETIME | 创建时间 | 默认 `CURRENT_TIMESTAMP` |
| `update_time` | DATETIME | 更新时间 | 自动更新 |

**索引**：`PRIMARY(user_id)`、`UNIQUE uk_user_name(user_name)`、`idx_user_role(role)`、`idx_user_email(email)`

### 1.5 `medication_record` —— 用药记录（依从性统计口径）

| 字段 | 类型 | 说明 | 约束 |
| :--- | :--- | :--- | :--- |
| `id` | INT | 记录主键 | **PK**，AUTO_INCREMENT |
| `user_id` | VARCHAR(32) | 所属老人 | NOT NULL |
| `medication_id` | INT | 关联 `medication.id` | NOT NULL，索引 `idx_mr_medication` |
| `plan_time` | VARCHAR(32) | 计划服用时间（`2026-09-21 08:00`） | NOT NULL，默认 `''` |
| `actual_time` | VARCHAR(32) | 实际服用时间（未服为空） | NOT NULL，默认 `''` |
| `status` | VARCHAR(8) | `待服` / `已服` / `漏服` | NOT NULL，默认 `待服`，索引 `idx_mr_status` |
| `create_time` | DATETIME | 创建时间 | 默认 `CURRENT_TIMESTAMP` |

**索引**：`PRIMARY(id)`、`idx_mr_user_time(user_id, plan_time)`、`idx_mr_medication`、`idx_mr_status`

**依从率计算**：`adherence_rate(user_id, days) = count(status='已服') / count(*)`

**初始化数据**：12 条近 7 天记录，覆盖 `已服` / `漏服` / `待服` 三种状态，便于演示周报"用药依从性"章节。

### 1.6 `alert_record` —— 健康告警记录

| 字段 | 类型 | 说明 | 约束 |
| :--- | :--- | :--- | :--- |
| `id` | INT | 告警主键 | **PK**，AUTO_INCREMENT |
| `user_id` | VARCHAR(32) | 告警所属老人 | NOT NULL |
| `alert_type` | VARCHAR(64) | `heart_rate_high` / `spo2_low` 等 | NOT NULL，默认 `''` |
| `level` | VARCHAR(8) | `高危` / `中危` / `低危` | NOT NULL，默认 `低危`，索引 `idx_alert_level` |
| `value` | VARCHAR(32) | 触发数值 | NOT NULL，默认 `''` |
| `metric` | VARCHAR(32) | 指标名（`heart_rate` 等） | NOT NULL，默认 `''` |
| `description` | VARCHAR(512) | 异常描述 | NOT NULL，默认 `''` |
| `source` | VARCHAR(16) | `auto` 自动检测 / `manual` 手动检测 | NOT NULL，默认 `auto`，索引 `idx_alert_source` |
| `status` | VARCHAR(8) | `待确认` / `已确认` | NOT NULL，默认 `待确认`，索引 `idx_alert_status` |
| `notify_result` | VARCHAR(256) | 通知结果留痕（短信/邮件/WS/Waiting 队列） | NOT NULL，默认 `''` |
| `create_time` | DATETIME | 告警时间 | 默认 `CURRENT_TIMESTAMP` |
| `confirm_time` | DATETIME | 家属确认时间 | NULL 允许 |

**索引**：`PRIMARY(id)`、**`idx_alert_user_time(user_id, create_time)`（时间轴查询主力索引）**、
`idx_alert_level`、`idx_alert_status`、`idx_alert_source`

**重要语义（AC-10）**：`detect_anomaly()` 是纯计算层，**不写本表**；
只有 `mode="auto"` 的 `detect_task.auto_detect_all` 才写。
因此连续调用手动检测 10 次，`AlertDAO.count_today(user_id)` 的行数不变。

**初始化数据（5 条）**：含 `source=auto` 与 `source=manual` 各若干，便于对比两种来源的统计口径。

### 1.8 `conversation_summary` —— 会话摘要（L2 摘要记忆）

| 字段 | 类型 | 说明 | 约束 |
| :--- | :--- | :--- | :--- |
| `session_id` | VARCHAR(64) | 会话编号（与 Checkpointer `thread_id` 一致） | **PK** |
| `user_id` | VARCHAR(32) | 会话归属用户 | NOT NULL，默认 `''`，索引 `idx_cs_user` |
| `summary` | TEXT | 会话历史摘要 | NOT NULL |
| `rounds` | INT | 已摘要的对话轮数 | NOT NULL，默认 0 |
| `update_time` | DATETIME | 更新时间 | 自动更新 |

**索引**：`PRIMARY(session_id)`、`idx_cs_user(user_id)`

> 生产环境的 L2 摘要记忆由 **PostgreSQL** 承载（`SummaryMemory` + `psycopg_pool`）；
> MySQL 这张同构表用于 PostgreSQL 不可用时的降级，保证接口语义不变。

## 2. 表关系说明

```
                    ┌──────────────────────┐
                    │        user          │
                    │  user_id (PK)        │
                    │  user_name (UNIQUE)  │
                    │  password / role     │
                    └───┬──────────┬───────┘
                        │          │
        ┌───────────────┘          └────────────────┐
        │ 1:1（老人档案）                            │ N:M（家属绑定）
        ▼                                           ▼
┌────────────────────┐                   ┌────────────────────────┐
│  health_profile    │                   │     elder_family       │
│  user_id (PK,FK)   │                   │  elder_id  (FK→user)   │
│  disease/allergy   │                   │  family_id (FK→user)   │
│  emergency_contact │                   │  UNIQUE(elder,family)  │
└────────────────────┘                   └────────────────────────┘
                                                        │
                     ┌──────────────────────────────────┘
                     │ 1:N（老人的用药/记录/告警）
        ┌────────────┴────────────┬──────────────────────┐
        ▼                         ▼                      ▼
┌────────────────┐      ┌────────────────────┐   ┌──────────────────┐
│  medication    │ 1:N  │ medication_record  │   │   alert_record   │
│  id (PK)       │─────►│ medication_id (FK) │   │  user_id (FK)    │
│  user_id (FK)  │      │ user_id (FK)       │   │  level/status    │
│  take_time     │      │ status 待服/已服/漏服│   │  source auto/manual│
└────────────────┘      └────────────────────┘   └──────────────────┘

    独立表（无外键，靠逻辑关联）：
    ┌──────────────────┐        ┌─────────────────────────┐
    │  knowledge_doc   │        │  conversation_summary   │
    │  doc_id (PK)     │        │  session_id (PK)        │
    │  disease_type    │        │  user_id（逻辑关联 user）│
    │  source/version  │        │  summary / rounds        │
    └──────────────────┘        └─────────────────────────┘
              │                              │
              │ 建库时同步到 Milvus           │ session_id == Checkpointer thread_id
              ▼                              ▼
      Milvus health_knowledge          Redis session:{uuid} / lock:session:{sid}
```

**关系约束说明**

| 关系 | 基数 | 说明 |
| :--- | :--- | :--- |
| `user` → `health_profile` | 1:1 | 老人本人一份档案（家属/管理员可不建） |
| `user` ↔ `user`（`elder_family`） | N:M | 一个家属可绑定多位老人，一位老人可有多个家属 |
| `user` → `medication` | 1:N | 老人的用药计划 |
| `medication` → `medication_record` | 1:N | 一条计划可产生多条服用记录 |
| `user` → `alert_record` | 1:N | 老人的告警记录 |
| `user` → `conversation_summary` | 1:N | 一个用户可有多个会话摘要 |
| `knowledge_doc` → Milvus | 1:1（逻辑） | 一个片段对应一条向量 + 元数据 |

**外键策略**：建表未使用物理 `FOREIGN KEY`，由 DAO 层保证引用一致性。
原因：并行开发期便于灌数据与清库；且数据权限过滤已在 DAO 强制 `where user_id = ...`，
越权风险不依赖外键（NFR-03）。

```
├──────────┼────────────────────────────────────────────────────────────────┤
│ time     │ 10 分钟粒度                                                     │
│          │ 服务启动时回填近 VITALS_BACKFILL_DAYS=7 天（约 1008 点/人）      │
│          │ 运行期 start_simulator 每 VITALS_INTERVAL_MINUTES=10 分钟写一条  │
└──────────┴────────────────────────────────────────────────────────────────┘
```

**InfluxQL / SQL 查询示例**

```sql
-- 最近 7 天心率序列
SELECT time, heart_rate FROM vital_signs
WHERE user_id = 'u001' AND time >= now() - INTERVAL '7 days'
ORDER BY time;

-- 近 7 天收缩压日均值（趋势检测的输入）
SELECT date_bin(INTERVAL '1 day', time) AS day, avg(blood_pressure_sys) AS avg_sys
FROM vital_signs
WHERE user_id = 'u001' AND time >= now() - INTERVAL '7 days'
GROUP BY day ORDER BY day;
```

**与检测层的对应**

| 检测层 | 读取方式 | 对应 `influx_tool` 函数 |
| :--- | :--- | :--- |
| ①规则阈值 | 只取最新一条 | `query_latest(user_id)` |
| ②统计趋势 | 取近 `TREND_DAYS=7` 天序列算移动平均与变化率 | `query_range(user_id, field, days=7)` |
| ③个性化离群 | 取近 30 天序列算 MAD / 训练孤立森林 | `query_range(user_id, field, days=30)` |
| 数据质检 | 取最新一条判断字段完整性 | `query_latest(user_id)` |

**保留期风险（R-02）**：InfluxDB 3 Core 不支持按点删除，脏数据只能等保留期过期或换库；
测试数据请用独立 database。

## 4. Redis Key 约定（需求文档 8.4）

| Key | 类型 | 说明 | TTL | 使用者 |
| :--- | :--- | :--- | :--- | :--- |
| `window_memory:{session_id}` | List | L1 窗口记忆，最近 N 轮原文，`rpush + ltrim` | `WINDOW_MEMORY_TIME`（默认 86400s = 1 天） | `WindowMemory` |
| `profile:{user_id}` | Hash | L4 用户画像：name/age/gender/disease_history/allergy/emergency_contact/emergency_phone/communication_preference/weaknesses | 长期（不设 TTL） | `ProfileMemory` |
| `session:{uuid}` | String | 会话归属：`user_id` + 创建时间；`/create_session` 校验用 | 1 天 | `HealthGraphAgent.check_session` |
| `lock:session:{session_id}` | String | 会话分布式锁（Lua 脚本原子释放），防同会话并发串话 | 5 分钟 | `HealthGraphAgent.chat` |
| `cache:profile:{user_id}` | String | 工具降级缓存（MCP/MySQL 不可用时的结果快照） | 1 小时 | `call_tool_with_fallback` |
| `pending_sms` | List | 模拟短信待发队列（未接真实短信网关，写日志 + 落队列） | 长期 | `mcp_server.tools.notify_tool.send_sms` |

**Celery 相关 Key（由 Celery 自己管理）**：broker 与 backend 都取 `REDIS_URL`（本项目 `.env` 为 db 1）。

**典型操作**

```python
# L1 窗口记忆写入
r.rpush(f"window_memory:{session_id}", json.dumps({"role": role, "content": content}, ensure_ascii=False))
r.ltrim(f"window_memory:{session_id}", -rounds * 2, -1)
r.expire(f"window_memory:{session_id}", settings.window_memory_time)

# L4 画像写入
r.hset(f"profile:{user_id}", mapping={"age": "72", "allergy": "青霉素", ...})

# 会话锁（不阻塞获取，失败提示"会话忙"）
got = r.set(f"lock:session:{session_id}", "1", nx=True, ex=300)
```

## 5. Milvus 集合设计

### 5.1 `health_knowledge` —— 健康知识向量（FR-09）

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | INT64（主键，auto_id） | 主键 |
| `vector` | FLOAT_VECTOR(dim) | 文本向量，维度由 `EMBEDDING_MODEL` 决定（text-embedding-v3 默认 1024） |
| `content` | VARCHAR(2048) | 知识片段正文（512 字符切分 + 100 重叠） |
| `title` | VARCHAR(256) | 文档标题 |
| `source` | VARCHAR(256) | 来源（《中国高血压防治指南》）—— **溯源字段** |
| `version` | VARCHAR(64) | 版本（2024修订版）—— **溯源字段** |
| `disease_type` | VARCHAR(64) | 病种，用于**元数据过滤** |
| `page` | VARCHAR(32) | 页码或章节 —— **溯源字段** |

**索引**：`vector` 建 `HNSW`（`metric_type=COSINE`，`M=16`，`efConstruction=200`）；
标量字段 `disease_type` / `source` 建 INVERTED 索引用于过滤。

**检索流程**

```
query → Embedding → Milvus Top-K（可带 disease_type 过滤表达式）
      → Rerank 精排（gte-rerank）
      → [{"content","source","version","page","score"}]   ← 每条可溯源（AC-14）
```

**降级**：Milvus 不可用 → `keyword_search`（MySQL `knowledge_doc`）→ 静态建议。

### 5.2 `long_memory` —— 长期记忆（FR-13 / L3）

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | INT64（主键，auto_id） | 主键 |
| `vector` | FLOAT_VECTOR(dim) | 记忆文本向量 |
| `user_id` | VARCHAR(32) | **过滤键**：检索时按 `user_id` 隔离，跨用户不串 |
| `content` | VARCHAR(2048) | 记忆内容（偏好、慢病史、家庭情况） |
| `create_time` | VARCHAR(32) | 写入时间（ISO 字符串） |

**索引**：`vector` 建 HNSW；`user_id` 建 INVERTED。

**写入时机**：每轮对话后由 `LongAgent.update(user_id, question)` 提取并写入。
**读取时机**：图执行前 `PromptBuilder` 检索并注入 system 提示词。

**降级链**：Milvus → ChromaDB（`CHROMA_PATH=./app/chroma_db`）→ 进程内内存字典，
三层都保证 `save/query` 接口语义一致。

## 6. 数据权限与脱敏

| 项 | 设计 |
| :--- | :--- |
| 数据权限 | 所有 DAO 查询强制拼 `where user_id = %s`；`can_access_user()` 决定"当前用户"能否代表目标 user_id |
| 老人 | 只能访问 `user_id == 自己` 的数据（越权返回 403，AC-19） |
| 家属 | 只能访问 `UserDAO.list_bound_elders(family_id)` 里的老人（未绑定 403，AC-20） |
| 管理员 | 全量可见（`can_access_user` 直接 True） |
| SQL 注入 | 全部 `%s` 参数化；`mysql_tool` 只读白名单，含 `DELETE/UPDATE/INSERT/DROP/CREATE/ALTER` 直接拒绝 |
| 日志脱敏 | 手机号中间打码（`139****0001`）、邮箱局部打码；不留存原始音频 |
| 密钥 | 全部在 `.env`，`.env` 进 `.gitignore`；`MCP_API_KEY` 不下发前端 |
